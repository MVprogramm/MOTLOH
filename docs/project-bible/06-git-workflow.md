# 06 — Git-процедура и обратимость

**Версия:** 1.0  
**Статус:** ACTIVE  
**Ответственность модуля:** определить порядок внесения изменений в Git и обеспечить проверяемость и обратимость каждого изменения.

---

## 1. Назначение

Git используется не только для хранения файлов, но и для фиксации последовательности утверждённых изменений проекта.

Каждое изменение должно быть:

- связано с конкретной задачей;
- ограничено необходимым набором файлов;
- понятно по истории коммитов;
- проверяемо после записи;
- обратимо без восстановления текста по памяти.

---

## 2. Основная ветка

Каноническое состояние проекта хранится в ветке `main`.

Материал считается действующей частью проекта только после внесения в `main`, если другой порядок не был отдельно утверждён владельцем проекта.

Черновики, обсуждения и локальные варианты вне `main` не считаются каноническими.

---

## 3. Подготовка изменения

Перед записью в Git необходимо:

1. получить актуальную версию `PROJECT_BIBLE.md`;
2. получить все действующие модули, относящиеся к задаче;
3. получить актуальную версию каждого изменяемого файла;
4. проверить, существует ли файл и каков его текущий SHA;
5. определить точную проблему и границы изменения;
6. убедиться, что правка не затрагивает несогласованные части проекта.

Нельзя выполнять изменение на основании сохранённой копии, памяти чата или предположения о текущем содержании файла.

---

## 4. Один коммит — одна задача

Один коммит должен решать одну основную задачу.

В один коммит допускается включать несколько файлов, только если их изменения непосредственно связаны и вместе образуют одно завершённое решение.

Нельзя объединять в одном коммите:

- независимые смысловые правки;
- изменение сценария и несвязанную переработку методологии;
- утверждённую правку и дополнительные улучшения, не входившие в задачу;
- содержательные изменения и массовое переформатирование без необходимости.

---

## 5. Сообщение коммита

Сообщение коммита должно кратко и однозначно описывать выполненное действие.

Рекомендуемая форма:

`<действие> <объект изменения>`

Примеры:

- `Add Git workflow module`
- `Clarify baseline approval rule`
- `Update scene 001 open questions`
- `Fix broken project bible link`

Сообщение не должно быть расплывчатым, например: `Update files`, `Changes`, `Fixes`.

---

## 6. Создание и обновление файлов

Новый файл создаётся только после проверки, что путь свободен и соответствует архитектуре репозитория.

Существующий файл обновляется только с использованием его актуального SHA.

Если GitHub сообщает о конфликте SHA или изменении файла после чтения, запись прекращается. Необходимо повторно получить актуальную версию, заново проверить правку и только затем выполнять обновление.

Полная замена содержимого файла не должна приводить к потере фрагментов, не относящихся к поставленной задаче.

---

## 7. Проверка после записи

После каждого изменения необходимо:

1. получить результат операции и SHA коммита;
2. повторно получить изменённый файл из ветки `main`;
3. проверить наличие внесённой правки;
4. проверить сохранность частей, которые не должны были измениться;
5. сообщить владельцу проекта SHA коммита и краткое содержание изменения.

Успешный ответ операции записи без проверки содержимого не считается достаточным подтверждением.

---

## 8. Обратимость

Каждое изменение должно допускать восстановление предыдущего состояния через историю Git.

Запрещено восстанавливать предыдущую версию вручную по памяти, по фрагментам из чата или путём приблизительного переписывания.

Перед откатом необходимо определить:

- какой коммит или состояние отменяется;
- к какой версии требуется вернуться;
- какие последующие изменения зависят от отменяемого решения;
- какие связанные файлы могут потребовать обновления.

Откат является новым изменением проекта и должен быть зафиксирован отдельным коммитом с понятным сообщением.

---

## 9. Удаление файлов

Файл удаляется только после проверки:

- что он больше не является действующим источником правил или материалов;
- что на него нет необходимых ссылок;
- что его содержание не должно быть перенесено в другой документ;
- что удаление явно соответствует поставленной задаче.

Удаление выполняется с использованием актуального SHA файла и фиксируется отдельным коммитом либо коммитом единой задачи, частью которой является это удаление.

---

## 10. Запрещённые действия

Без отдельного явного решения владельца проекта запрещено:

- переписывать историю ветки `main`;
- использовать принудительное обновление ветки;
- объединять независимые задачи в один коммит;
- удалять историю ради упрощения репозитория;
- изменять файлы, не относящиеся к поставленной задаче;
- создавать параллельную каноническую версию одного материала;
- считать запись успешной без последующей проверки.

---

## 11. Критерий завершения Git-операции

Git-операция считается завершённой только при одновременном выполнении четырёх условий:

1. изменение внесено в предназначенный файл;
2. изменение находится в ветке `main`;
3. содержимое повторно проверено после записи;
4. SHA коммита сообщён владельцу проекта.

Если хотя бы одно условие не выполнено, задача считается незавершённой.
