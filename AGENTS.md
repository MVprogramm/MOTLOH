# SCREENPLAY AI — инструкции для Codex

## Язык работы

- Методологические документы писать на русском языке.
- Названия папок и файлов писать на английском языке.
- Сценарный текст писать на языке текущего сценария.

## Источник истины

Перед любым анализом или изменением файлов:

1. Прочитать актуальный `PROJECT_BIBLE.md`.
2. Прочитать все модули, относящиеся к текущей задаче.
3. Для работы со сценами, сюжетом, персонажами, визуальными образами или финалом прочитать `docs/THEME.md`.
4. Прочитать непосредственно редактируемый файл.
5. Работать только на основании актуального состояния репозитория.
6. Не восстанавливать отсутствующий текст по памяти или по содержанию предыдущих чатов.
7. Не изменять BASELINE без явного разрешения владельца проекта.

## Правила изменения файлов

Перед записью:

1. Проверить, существует ли файл и каков его текущий SHA.
2. Сформулировать точную задачу и границы изменения.
3. Вносить только согласованную правку.
4. Не изменять соседний текст без необходимости.
5. Не объединять независимые задачи в один коммит.

После записи:

1. Повторно получить изменённый файл из ветки `main`.
2. Проверить наличие внесённой правки.
3. Проверить сохранность частей, которые не должны были измениться.
4. Сообщить SHA коммита и кратко описать изменение.

## Работа со списком сцен

Список сцен хранится в:

`docs/story/scene-list.md`

Перед созданием пакета сцены соответствующая строка должна быть утверждена в списке сцен.

Не добавлять и не изменять строку списка сцен без явного утверждения владельца проекта.

## Работа с пакетом сцены

Пакет сцены создаётся согласно:

`docs/project-bible/04-scene-package.md`

Не писать Fountain до завершения обязательных подготовительных документов, если владелец проекта явно не распорядился иначе.

## Стиль взаимодействия

- Сначала анализировать и предлагать формулировку.
- Не записывать предложение в репозиторий до явного утверждения владельца проекта.
- При неоднозначности задавать один конкретный вопрос.
- Не переписывать целые документы ради локальной правки.
- Чётко отделять утверждённые решения от предложений и рабочих вариантов.
